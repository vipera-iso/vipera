# HTTP API

Vipera serves the OpenAI Chat Completions protocol with server-sent events
(SSE) streaming. One gateway process serves exactly one model.

Start it with:

```bash
vipera serve start --model <alias>
# → http://127.0.0.1:8686
```

The API has no authentication. Any `Authorization`/`api_key` value is accepted
and ignored. Bind to `127.0.0.1` (the default) unless you put a reverse proxy in
front of it.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | Liveness and active model alias. |
| `GET` | `/v1/models` | OpenAI-shaped model list (one entry). |
| `POST` | `/v1/chat/completions` | Chat completion, streaming or not. |
| `GET` | `/docs` | Interactive OpenAPI UI generated by FastAPI. |
| `GET` | `/openapi.json` | OpenAPI schema. |

`/health`, `/docs`, and `/openapi.json` are Vipera/FastAPI conveniences;
`/v1/models` and `/v1/chat/completions` are the OpenAI-compatible surface.

### `GET /health`

```json
{ "status": "ok", "model": "deepseek-v2-lite" }
```

The `model` value is the registry alias used at startup. The endpoint does not
check that the engine is still healthy beyond the process being alive.

### `GET /v1/models`

```json
{
  "object": "list",
  "data": [
    { "id": "deepseek-v2-lite", "object": "model", "owned_by": "vipera" }
  ]
}
```

`id` is the alias, so `model="default"` in a request is not required — use the
alias, or anything else; see below.

### `POST /v1/chat/completions`

Request body:

| Field | Type | Default | Notes |
|---|---|---|---|
| `model` | `string \| null` | `null` | Accepted for compatibility and **ignored**. |
| `messages` | `array` (min 1) | required | See message schema. |
| `stream` | `boolean` | `false` | Enables SSE. |
| `temperature` | `number` | `0.7` | Forwarded to `llama.cpp`. |
| `max_tokens` | `integer` | `2048` | Forwarded to `llama.cpp`. |
| `top_p` | `number` | `0.95` | Forwarded. |
| `repeat_penalty` | `number` | `1.1` | Forwarded. |

Message object:

| Field | Type | Notes |
|---|---|---|
| `role` | `"system" \| "user" \| "assistant" \| "tool"` | Validated; anything else is a 422. |
| `content` | `string` | Required. Array-of-parts content (text + image) is **not** supported. |

Extra fields such as `tools`, `tool_choice`, `response_format`, `stop`,
`presence_penalty`, and `seed` are not part of the model and are ignored by
Pydantic; they do not reach the engine. Tool calling is not implemented.

#### Non-streaming

```bash
curl http://127.0.0.1:8686/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "messages": [{"role": "user", "content": "Hello!"}]
  }'
```

The gateway returns the dictionary produced by
`llama_cpp.Llama.create_chat_completion` without rewriting it:

```json
{
  "id": "chatcmpl-...",
  "object": "chat.completion",
  "created": 1760000000,
  "model": "...",
  "choices": [
    {
      "index": 0,
      "message": { "role": "assistant", "content": "Hello! How can I help?" },
      "finish_reason": "stop"
    }
  ],
  "usage": { "prompt_tokens": 8, "completion_tokens": 7, "total_tokens": 15 }
}
```

The `model` value comes from `llama.cpp`; Vipera does not replace it with the
registry alias. Use `/v1/models` or `/health` if you need the alias.

#### Streaming

```bash
curl -N http://127.0.0.1:8686/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "messages": [{"role": "user", "content": "Count to 5."}],
    "stream": true
  }'
```

Response headers include `content-type: text/event-stream`. Each chunk is one
SSE data event:

```text
data: {"id":"chatcmpl-...","object":"chat.completion.chunk","created":1760000000,"model":"...","choices":[{"index":0,"delta":{"content":"One"},"finish_reason":null}]}

data: {"id":"chatcmpl-...","object":"chat.completion.chunk","created":1760000000,"model":"...","choices":[{"index":0,"delta":{"content":" and"},"finish_reason":null}]}

data: [DONE]

```

Details that matter when writing a client:

- `data: [DONE]` is always sent, including after an error.
- There is no `event:` field and no blank keep-alive frame; only `data:` lines.
- The final content chunk may carry `finish_reason`; clients should not depend
  on which chunk contains it.
- If generation raises mid-stream, the HTTP status is already `200`. Vipera
  emits `data: {"error": {"message": "..."}}` and then `[DONE]`. OpenAI SDKs do
  not expect that frame; check the pipeline outside the SDK if you need to
  surface it.

#### Errors

| Status | When |
|---|---|
| `400` | Explicit empty-`messages` guard. In practice Pydantic's `min_length=1` returns 422 first. |
| `422` | Validation failure: missing `messages`, unknown role, non-string content, wrong types. |
| `500` | Unhandled server error outside generation (generation errors in streaming mode become SSE frames). |

Error bodies follow FastAPI's `{"detail": ...}` format, not OpenAI's
`{"error": {...}}` envelope.

## Client examples

### Python (`openai`)

```python
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:8686/v1", api_key="none")

stream = client.chat.completions.create(
    model="default",  # ignored by the gateway
    messages=[{"role": "user", "content": "Explain MoE in one paragraph."}],
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")
```

### JavaScript (`openai`)

```js
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "http://127.0.0.1:8686/v1",
  apiKey: "none",
});

const stream = await client.chat.completions.create({
  model: "default",
  messages: [{ role: "user", content: "hi" }],
  stream: true,
});

for await (const chunk of stream) {
  process.stdout.write(chunk.choices[0]?.delta?.content ?? "");
}
```

### Raw HTTP client

Read the response incrementally and split on `\n\n`; do not buffer the whole
body, or you lose streaming. Treat `[DONE]` as terminal. Because chunks are
flushed per token by the server, `curl -N` (or an equivalent unbuffered client)
shows them as they arrive.

## Concurrency and limits

- All completions are serialized by a process-wide lock. A second request waits
  until the first finishes, including while it is streaming.
- There is no request timeout, queue limit, token limit beyond `max_tokens`, or
  rate limiting.
- No CORS middleware is installed. Browser clients on another origin will be
  blocked unless you proxy through the same origin or add middleware.
- Request bodies are validated only for the fields listed above; unknown fields
  are dropped silently rather than rejected.

## Compatibility checklist

| OpenAI feature | Status |
|---|---|
| `POST /v1/chat/completions` | Supported |
| SSE streaming | Supported, custom termination frame is standard `[DONE]` |
| `GET /v1/models` | Supported, single model |
| `model` request field | Accepted, ignored |
| `system`/`user`/`assistant` messages | Supported |
| `tool` role and tool calls | Role accepted; tool calling not implemented |
| Multimodal content parts | Not supported |
| `POST /v1/completions` | Not implemented |
| `POST /v1/embeddings` | Not implemented |
| OpenAI-style error envelope | Not implemented |
| API key auth | Not implemented |
| CORS | Not implemented |
